# honestdocs v1: the method and CLI, made general

## Context

Glivo, a desktop automation app built largely with AI coding agents, kept about 260
development documents in a private folder with a handful of scripts: documents typed by
purpose, fields derived from git, a `Doc:` commit trailer linking work to its document, a
`rules/` folder of numbered rules every feature had to keep. It worked — and it was bound
to that project: Bun-only, paths and titles hard-coded, one layout.

Looking at what else exists:

- **ADR tools** (adr-tools, log4brains, the MADR template) cover one kind of document —
  the decision — with no progress, no link to code, no lifecycle beyond accepted /
  superseded.
- **Big-project processes** (Rust RFCs, Python PEPs, Kubernetes KEPs) carry metadata kept
  in sync by hand; the Kubernetes release process names exactly that as a pain: kep.yaml,
  issues and a tracking sheet drifting apart.
- **Spec-driven kits** (GitHub Spec Kit, OpenSpec, Kiro) structure what an agent is told
  *before* it writes code. Spec Kit's "constitution" is close to our `rules/`, but as
  prose with nothing that checks it.

None derives a document's files from commit trailers, counts its progress, or fails CI
when a replaced document still claims to be current. That is the part worth sharing.

## Goals / Non-goals

Goals:

- One CLI anyone can run with `npx`: zero dependencies, Node 20+ and Bun, Windows, macOS
  and Linux.
- Everything project-specific in a config file: areas, folder, title, trailer, the code
  repositories, templates, types.
- The method written down for people (`METHOD.md`) and for agents (an AGENTS.md section
  and a skill), with commands built for agents: `brief`, `search`, `rules`, `--json`.
- Three layouts: same repository, a nested documents repository, several code
  repositories.

Non-goals for v1:

- A website or renderer — Markdown on GitHub is enough.
- An MCP server — the CLI with `--json` already serves agents.
- Writing document content with AI — the tool keeps the frame honest, people and agents
  write the words.
- `adopt`, for bringing an existing folder of documents under the tool.

## Decision

Port the Glivo scripts into a package with a dispatcher (`bin/honestdocs.mjs`), shared
modules in `src/`, and one file per command. Keep the derivation rules exactly; change
what generality demands:

- **Two lifecycles.** Glivo's four rule documents sat at `draft` for weeks while everyone
  followed them, because "draft → in-progress → done" does not fit something that is never
  finished. Living documents (`reference`, `rule`) get `draft → current → retired`.
- **Whole-id trailer matching, one git call.** The old `git log --grep "Doc: <id>"` per
  document matched prefixes (`…-auth` counted commits for `…-auth-tokens`) and spawned a
  process per document. Now one `git log` is parsed for every trailer.
- **Renames followed by parsing `--name-status -M`**, so moving a folder of documents does
  not restamp their `updated`, without a `--follow` call per file.
- **An index with no timestamp**, so `check` can tell a stale INDEX.md from a fresh one.
  Glivo's had drifted two days without anyone noticing.
- **Errors versus warnings by who can fix them.** `progress`, `superseded-by`, a stale
  index — fixable before the commit — are errors. `files` and `updated` move with every
  commit that names the document, so they are warnings; otherwise CI would demand a
  follow-up commit forever.
- **Rules are parsed.** `- **R1** …` with an indented `Test:` line; `check` fails when a
  named test file is gone or two rules share an id.

## Alternatives considered

- **Derived fields not stored at all, computed on demand.** Nothing could ever be stale.
  Rejected: on GitHub, in an editor, to an agent reading a file, the frontmatter is what
  people see; a document that does not say what it touched loses most of its value.
- **Failing CI on any stale derived field.** Rejected: a commit carrying `Doc: <id>`
  makes that document's `files` stale by definition, so every code commit would need a
  docs commit after it.
- **Requiring Bun, as the original scripts did.** Rejected: most projects that would use
  this have Node and no Bun. The code stays plain enough for both.
- **A YAML library for frontmatter.** Rejected under H1. A flat subset is all the format
  needs, and a strict shape is what lets `check` say something precise.
- **A Glivo-branded name or an `@glivo/` npm scope.** Rejected: people skip a tool whose
  name says it belongs to another product, and the name would have to follow any future
  rename of that product. The origin is told in the README instead.
- **Only ADRs**, to compete with the existing tools on their ground. Rejected: research,
  plans, postmortems and standing rules are where most of the value lies.

## Verification

```sh
node --test
node bin/honestdocs.mjs index && node bin/honestdocs.mjs check
```

Against a real set: a scratch config pointing `root` and `codeRepos` at another project,
then `index --dry-run --json` and `check --json` — nothing is written.
